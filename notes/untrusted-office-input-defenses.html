Defensive Screening Before LLM Triage: Untrusted Emails, Attachments, and CSVs

Back-office operational workflows—accounts payable, vendor onboarding, remittance matching—sit directly on an unauthenticated external boundary: anyone can send an email, attach an "invoice," or submit a CSV schedule. This note details the deterministic pre-LLM screening architecture implemented in inbox-guard.

1. Why Back-Office LLM Triage Needs a Deterministic Pre-Filter

Operational email pipelines combine two distinct risk surfaces:

  1. Classical document & spreadsheet hazards aimed at human reviewers: disguised executables claiming a .pdf extension, Unicode bidirectional filename spoofing, and spreadsheet formula/DDE payloads exported into reconciliation queues opened in Excel, LibreOffice Calc, or Google Sheets.
  2. Model-boundary hazards aimed at automated triage: invisible Unicode characters or zero-opacity HTML blocks that human reviewers never see in a rendered preview but HTML-to-text extractors feed verbatim into language-model prompts, alongside raw personal and banking identifiers crossing external API boundaries.

inbox-guard isolates these checks into a small, auditable, zero-dependency ES module library (using only Node's built-in node:test runner and verified with CodeQL) that runs before inbound artifacts touch a parser, model API, or operator queue.

2. Attachment Screening: Magic Bytes, Double Extensions & Bidi Spoofing

Relying on MIME headers or path.extname() alone fails against trivial filename and content spoofing. In src/attachment.mjs, checkAttachment({ filename, headBytes }) evaluates metadata and leading file bytes independently, accumulating structured severity-graded findings rather than short-circuiting on the first match:

Unicode Bidirectional Override (U+202E) & Path-Traversal Checks

Unicode Right-to-Left Override (U+202E) and directional isolate/embedding characters (U+202A..U+202E, U+2066..U+2069) reverse the visual display order of subsequent characters without changing the underlying code-point sequence read by an OS shell. For example, the raw string invoice_\u202Efdp.scr terminates in .scr (a Windows screensaver executable), yet renders visually to an accounts-payable clerk as invoice_rcs.pdf.

checkAttachment rejects any filename matching /[\u202A-\u202E\u2066-\u2069]/ (UNICODE_BIDI_SPOOF), ASCII control or null bytes /[\x00-\x1F\x7F]/ (CONTROL_CHAR_FILENAME), and directory separators or parent-directory segments (/, \, .. → PATH_TRAVERSAL_FILENAME).

Extension Policy & Double-Extension Decoys

Terminal extensions are checked against a 38-entry blocklist (BLOCKED_EXTENSIONS) covering native binaries and installers (.exe, .scr, .msi, .dll, .app, .pkg), disk images and shortcuts (.lnk, .iso, .img, .vhd, .dmg), shell/script formats (.ps1, .vbs, .hta, .wsf, .jar, .command, .sh), and macro-enabled Office templates (.docm, .xlsm, .pptm, .dotm, .xltm). When a multi-dot filename pairs a benign decoy penultimate token (pdf, csv, xlsx, docx, png, etc.) with a blocked terminal extension—such as PO_Revision_1042.pdf.exe—it additionally emits DOUBLE_EXTENSION_DECOY.

Leading Magic-Byte Header Verification

When leading bytes (headBytes, e.g., the first 512 bytes read by bin/inbox-guard.mjs) are supplied, checkAttachment inspects binary signatures independent of claimed filename:

Finding Code Byte Signature / Condition Defensive Rationale
EXECUTABLE_MAGIC_BYTES 4D 5A (MZ PE), 7F 45 4C 46 (\x7FELF), or Mach-O CF FA ED FE / FE ED FA CF / CA FE BA BE Flags native Windows, Linux, and macOS universal binaries even when renamed to wire-instructions.pdf.
PDF_HEADER_MISMATCH Extension is .pdf without leading 25 50 44 46 2D (%PDF-) Rejects non-PDF payloads (archives, scripts, PE binaries, or corrupted blobs) masquerading as PDFs before downstream PDF text extraction.
PNG_HEADER_MISMATCH Extension is .png without 8-byte PNG signature 89 50 4E 47 0D 0A 1A 0A Verifies genuine PNG framing prior to OCR or vision-model ingestion.
HTML_SCRIPT_IN_PLAINTEXT Extension is .csv or .txt whose first 256 UTF-8 bytes contain <script, <!doctype html, or <html Catches HTML smuggling and browser-executed script documents disguised as plaintext accounting exports.

3. Accounting-Safe OWASP CSV Formula Neutralization

When untrusted vendor fields (memo lines, payee names, invoice notes) or LLM-extracted tables are exported to CSV and opened in spreadsheet software, cells starting with =, +, -, or @—including cells preceded by leading tabs or newlines—are interpreted as executable formulas or Dynamic Data Exchange (DDE) commands (e.g., =WEBSERVICE(...), =IMPORTXML(...), or tab-prefixed \t=HYPERLINK(...)).

Standard OWASP CSV Injection guidance recommends prefixing a single quote (') to every cell starting with =, +, -, or @. In financial back-office software, applying that rule blindly breaks production accounting workflows: legitimate credit memos and negative balances like -1250.00, -1,420.55, or -4.25% begin with -, and turning them into single-quoted text strings breaks downstream summation and ledger reconciliation.

In src/csv.mjs, isFormulaInjectionCell and sanitizeCsvRows resolve this tension deterministically: 

const FORMULA_TRIGGERS = new Set(["=", "+", "-", "@"]);
const PLAIN_NEGATIVE_NUMBER_RE = /^-\d+(?:,\d{3})*(?:\.\d+)?%?$/;

export function isFormulaInjectionCell(value, { allowNegativeNumbers = true } = {}) {
  if (typeof value !== "string" || value.length === 0) return false;
  const trimmedStart = value.replace(/^[\t\r\n ]+/, "");
  if (trimmedStart.length === 0) return false;

  const first = trimmedStart[0];
  if (value[0] === "\t" || value[0] === "\r" || value[0] === "\n") {
    if (FORMULA_TRIGGERS.has(first)) return true;
  }

  if (!FORMULA_TRIGGERS.has(first)) return false;
  if (first === "-" && allowNegativeNumbers && PLAIN_NEGATIVE_NUMBER_RE.test(trimmedStart.trim())) {
    return false;
  }
  return true;
}
  • Control-whitespace bypasses stay blocked: Any cell beginning with \t, \r, or \n followed by a formula trigger immediately returns true and is neutralized with a leading '.
  • Strict numeric grammar for negative figures: Only plain negative integers, comma-grouped thousands, decimals, and percentages matching /^-\d+(?:,\d{3})*(?:\.\d+)?%?$/ pass untouched when allowNegativeNumbers is enabled. Expressions containing operators, cell references, or function calls after a leading minus (such as -2+3 or -A1) fail the regex and are neutralized alongside structured { row, column, originalPreview } audit coordinates.

4. Concealed Text: Plane-14 Unicode Tags & CSS-Hidden Overrides

Indirect prompt injection in email triage frequently exploits discrepancies between what a human operator sees in a mail client and what a downstream text extractor passes to a model. src/email.mjs (inspectInboundEmail) screens four distinct layers:

  1. Sender vs. Reply-To domain divergence (REPLY_TO_DOMAIN_MISMATCH): Extracts and compares domain suffixes on From and Reply-To headers, flagging cross-domain reply redirection (e.g., ap@supplier.example paired with collector@wire-redirect.example).
  2. Zero-width & Plane-14 Unicode Tag stripping (INVISIBLE_UNICODE_CHARS): Matches zero-width spaces/joiners (U+200B..U+200F, U+2060..U+2064, U+FEFF), bidi controls (U+202A..U+202E, U+2066..U+2069), and Plane-14 Unicode Tag characters (U+E0000..U+E007F, encoded in JavaScript UTF-16 strings as surrogate pairs \uDB40[\uDC00-\uDC7F]). Severity escalates from low (incidental BOM/joiner) to high when 8 or more invisible code points appear, and all matched code points are stripped from sanitizedSubject and sanitizedText.
  3. CSS-hidden HTML blocks (HIDDEN_HTML_CONTENT): Scans raw HTML inline styles for display:none, visibility:hidden, opacity:0 (using negative lookahead (?![.\d]) so legitimate styles like opacity:0.85 are not false-flagged), and zero-sized text (font-size:0 with optional units).
  4. Normalization-first override pattern scan (INSTRUCTION_OVERRIDE_PATTERN): Critically, inspectInboundEmail strips INVISIBLE_UNICODE_RE before evaluating instruction-override patterns so zero-width characters interleaved inside words cannot evade token matching.

5. Deterministic Session-Scoped PII Tokenization

Even after screening attachments and hidden markup, passing raw customer SSNs, bank/card account numbers, phone numbers, or email addresses to an external model API expands data-exposure scope unnecessarily—especially when the model only needs entity relationships to classify an inquiry or draft a response template.

In src/redact.mjs, createRedactor() provides deterministic, session-scoped tokenization:

  • Case-normalized entity stability: Lookup keys are normalized via `${kind}:${rawValue.toLowerCase()}` inside an ephemeral per-session Map. Within a single triage session, both jane.doe@example.com and JANE.DOE@example.com resolve to <EMAIL_1>, preserving coreference across multi-message threads while keeping the mapping strictly in local memory.
  • Ordered pattern precedence: redact() applies EMAIL_RE, SSN_RE (excluding invalid SSN prefixes 000, 666, and 9xx), LONG_ACCOUNT_RE (12–19 digit sequences), and PHONE_RE in strict order—running LONG_ACCOUNT_RE before PHONE_RE so 16-digit account/card numbers are never partially tokenized as 10-digit phone numbers.
  • Local restoration for human review: Once a draft response is returned, redactor.restore(draft) substitutes local tokens (<EMAIL_1>, <ACCOUNT_1>) back to original values strictly inside the local boundary for human review.

6. Architectural Boundaries & Limitations

Deterministic input screening reduces attack surface substantially, but syntactic filters alone cannot guarantee immunity against open-ended semantic prompt injection in natural-language prose. In production systems (including the design of Kestrel), inbox-guard is paired with three structural invariants:

  • Deterministic arithmetic: Totals, variances, and ledger balances are computed in deterministic code—never delegated to language-model token prediction.
  • Least-privilege context: Identifiers are tokenized locally prior to external API calls, and cross-session token maps are never shared across tenants.
  • Human-gated execution: Language-model outputs are staged strictly as reviewable drafts; outbound emails, wire approvals, and ledger mutations require explicit human action.
